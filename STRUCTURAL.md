# Structural coverage

What the client is *proven* to do when the network, the controller or the clock
misbehaves - as opposed to what it does on a good day, which is
[COVERAGE.md](docs/COVERAGE.md) and the README tables.

Regenerated by `npm run structural`. Loop definition:
`docs/tasks/structural-coverage-loop.md`. Machine state:
`docs/structural/state.json`.

**0 verified · 0 failing · 30 untested · 0 manual-only · 0 excluded** (of 30 cells)

Every cell is one scenario on one protocol generation. A cell is `verified`
only when a test asserting it ran green against a live controller; a cell with
no test is `untested`, never assumed.

## Cells

### S01-drop-midrequest - Connection drop mid-request

**rws1** - untested

- plain GET mid-flight -> typed RwsError, never an uncaught throw
- mastership-guarded POST mid-flight -> mastership released or reacquirable, no stuck hold
- file transfer mid-flight -> typed error, no partial file silently accepted
- quality reflects the drop (stale or polling), never stays live

**rws2** - untested

- plain GET mid-flight -> typed RwsError, never an uncaught throw
- mastership-guarded POST mid-flight -> write access released or reacquirable
- file transfer mid-flight -> typed error, no partial file silently accepted
- quality reflects the drop (stale or polling), never stays live

### S02-half-open-freeze - Half-open freeze (sockets alive, no forwarding)

**rws1** - untested

- heartbeat detects within 2x ping interval
- frozen socket is terminated, reconnect path runs
- onLost fires at most once if the budget is exhausted
- onRestored fires after recovery

**rws2** - untested

- app-level PING/PONG deadline detects within 2x ping interval
- frozen socket is terminated, re-POST /subscription runs
- onLost fires at most once if the budget is exhausted
- onRestored fires after recovery

### S03-warm-restart - Controller warm restart

**rws1** - untested

- mid-session: silent re-auth, consumer sees no error
- mid-subscription: subscriber re-registers, events resume
- mid-mastership-hold: hold is not falsely believed after restart
- RWS port may DRIFT on IRC5 (new RobVC process) - client or test must rediscover

**rws2** - untested

- mid-session: fresh session cookie adopted (old one is dead)
- mid-subscription: re-POST + WS upgrade with the NEW cookie, not the stale one
- mid-write-access-hold: control-station registration re-established
- quality returns to live/polling, not stuck reconnecting

## Known limits

- Live cells run against **localhost virtual controllers only**; the helper in
  `tests/helpers/liveControllers.ts` refuses any other host outright.
- VC RWS ports drift across restarts, so they are discovered every run rather
  than configured. Override with `RWS_TEST_PORT_RW6` / `RWS_TEST_PORT_RW7`.
- Warm restart is the destructive ceiling. No cell resets a system, restores a
  backup, runs an installer, or mutates UAS.
- IK/FK failures on a VC are a missing option (PC Interface 616-1), not a defect.
