misbehaves - as opposed to what it does on a good day, which is
[COVERAGE.md](docs/COVERAGE.md) and the README tables.

`docs/tasks/structural-coverage-loop.md`. Machine state:
`docs/structural/state.json`.

only when a test asserting it ran green against a live controller; a cell with

### S05-session-slot-pressure - Session-slot pressure over reconnect cycles

**rws1** - **FAILING** (1 passed, 3 failed)

- repeated connect/disconnect reuses slots - controller session count flat
- disconnect issues GET /logout (clearSession is a deliberate no-op)
- IRC5 caps at 70 sessions; churn must not approach it
- EVIDENCE 2026-08-09, measured OUTSIDE the cell with a paired control: 30 connect/disconnect cycles WITH disconnect all succeed, and the same loop WITHOUT disconnect fails at cycle 2 with CONTROLLER_BUSY. So the client does free its slot, and the method would unmistakably detect it if it did not. The cell's own 503s are environmental: after a long test session the IRC5 sits near its cap (leaked sessions linger 300 s), so any additional concurrent client trips it. Re-run against a freshly restarted IRC5.

Failures:

- `S05-session-slot-pressure/rws1 > reconnect cycles leave the controller session count flat` - Controller busy (503) - retry later
- `S05-session-slot-pressure/rws1 > reconnect cycles do not open a connection per request` - Controller busy (503) - retry later
- `S05-session-slot-pressure/rws1 > RobotManager reconnect cycles stay flat and leave quality honest` - Controller busy (503) - retry later

**rws2** - **FAILING** (2 passed, 4 failed)

- EXCLUDED sub-property: 'controller session count flat' is NOT OBSERVABLE on RWS 2.0. The cell's own premise guard demonstrated it: connecting a client leaves GET /users unchanged (2 -> 2), so that list enumerates users, not sessions. A measurement that cannot see one deliberate session cannot see twenty accidental ones, and the test correctly refuses to assert a leak it cannot detect rather than reporting a false 'flat'.
- credentials are not re-sent once a session cookie is held
- subscription re-POST rides the existing session (no new session per subscribe)
- OPEN: the two properties above need a mock HTTPS server to assert - a TCP chaos proxy cannot read TLS headers, so wire-level claims are unobservable through it on this generation

Failures:

- `S05-session-slot-pressure/rws2 > reconnect cycles leave the controller session count flat` - connecting a client left GET /users unchanged (2 -> 2) - the session count is not observing our sessions, so no leak below could ever fail it: expected 2 to be greater than 2

### S15-soak - 24 h soak with periodic injected faults

**rws1** - manual-only

- RSS drift within threshold
- handle/socket count flat
- zero uncaught exceptions
- final state matches controller truth

> Occupies the machine ~24 h; scheduling is a human checkpoint per the task doc.

**Manual procedure**

1. Restart both VCs so no session backlog is carried in.
2. `node scripts/soak.mjs --minutes 1440` (add `--rss-drift-mb` / `--handle-growth` to override the thresholds).
3. Leave the machine otherwise idle - the run holds a manager against each generation and injects a fault every 15 s.

Thresholds are fixed BEFORE the run, in the script, so the verdict cannot be rationalised afterwards:
- **RSS drift** <= 75 MB from a POST-WARMUP baseline (warm-up excluded because the first minute is lazy imports and JIT, which never recur).
- **Handle growth** <= 5 for any single active-handle kind. Sockets and timers are what leak here; one socket in TIME_WAIT is noise, sustained growth is not.
- **Uncaught exceptions** exactly 0. Any unhandled rejection fails the soak outright regardless of memory.
- **Final state** must match an INDEPENDENT client's reading, not the manager's own cached view.

Output lands in `docs/structural/soak-<timestamp>.json`. A scaled run is written with `scaled: true` and is evidence the harness works, NOT the acceptance run.

## Running the loop

```bash
npm run structural          # run the auto cells, regenerate this file + state.json
npm run structural -- --no-run   # re-map the LAST run's results (after editing the matrix)
npm run structural -- --strict   # non-zero exit while any cell is failing or untested
node scripts/soak.mjs --minutes 1440   # S15 acceptance run (see below)
```

Cells run **serially** (`--no-file-parallelism`). Vitest parallelises files by
default, which would put several live clients on one controller at once; each
paces itself correctly but nothing coordinates across clients, and the pair
exceeds the controller's <20 req/s ceiling.

**Start from a freshly restarted controller.** Sessions linger for 300 s, so a
controller that has just run a long suite sits near its cap and answers 503 to
anything extra - which fails cells for a property they are not testing.

## Known limits

- Direct session counting is **not observable on RWS 2.0**: `GET /users`
  enumerates users, not sessions, so it does not move when a client connects.
  S05's premise guard detects this and refuses to assert a leak it cannot see.
- A half-open state affecting **only** the RWS 2.0 subscription WebSocket, while
  HTTP still works, cannot be detected in band: the controller rejects client
  frames on that socket and an idle subscription sends nothing back. Detection
  covers link-level failure.
- TLS is opaque to the TCP chaos proxy, so wire-level assertions (headers,
  request lines) are only possible on RWS 1.0 or against a mock HTTPS server.
- Live cells run against **localhost virtual controllers only**; the helper in
  `tests/helpers/liveControllers.ts` refuses any other host outright.
- VC RWS ports drift across restarts, so they are discovered every run rather
  than configured. Override with `RWS_TEST_PORT_RW6` / `RWS_TEST_PORT_RW7`.
- Warm restart is the destructive ceiling. No cell resets a system, restores a
  backup, runs an installer, or mutates UAS.
- IK/FK failures on a VC are a missing option (PC Interface 616-1), not a defect.
